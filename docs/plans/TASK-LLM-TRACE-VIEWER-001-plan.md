# TASK-LLM-TRACE-VIEWER-001 Plan — LLM Trace Viewer

This is the canonical implementation plan for TASK-LLM-TRACE-VIEWER-001. It records current-architecture evidence and the smallest change that lets developers inspect traces produced by TASK-LLM-TRACE-001.

**Gate:** `plan_review` — awaiting plan approval before any product/code implementation (`plan_approved=true`).

Writing this file is not Done for the task. Implementation of product code is forbidden until that gate is recorded after Plan review.

**Hard constraints (Plan + Implementation):**

- Do not modify TASK-LLM-TRACE-001 write-path behavior unnecessarily (`withLlmTrace`, `LLMInteractionTrace` shape, `plt.llm_trace.v1` key/version).
- Do not implement Memory, Learning Controller, Prompt Optimization, or an AI evaluation system.
- Do not expand Domain / Conversation / Workspace semantic contracts.
- Keep MVP local-first and developer-facing; no accounts, collaboration, or remote telemetry.

---

## Goal

Developers can list and inspect LLM interaction traces generated by the Chat API, without changing how traces are recorded.

```text
Chat API (existing write path)
  → withLlmTrace → LlmTraceStore (plt.llm_trace.v1)
       ↓ read path (new)
  GET /api/llm-traces[/:id]
       ↓
  Trace Viewer UI (developer tool)
```

## Current-state findings

### 1. LLM provider layer

| Piece | Path | Role |
| --- | --- | --- |
| `LlmProvider` | `src/infrastructure/llm/types.ts` | `complete(NodeChatRequest) → NodeChatAiResponse` |
| DeepSeek | `src/infrastructure/llm/deepseek.ts` | Live provider; no store/trace imports |
| Mock | `src/infrastructure/llm/mock.ts` | Deterministic provider; no store/trace imports |
| Middleware | `src/infrastructure/llm/with-trace.ts` | Provider-agnostic wrap; appends `LLMInteractionTrace` on success/error |

Trace recording is already middleware-owned. Providers must stay free of persistence/trace logic.

### 2. Chat API

[`server/chat-api.ts`](../../server/chat-api.ts):

- Creates process-local `createMemoryLlmTraceStore()` unless injected.
- Wraps configured provider with `withLlmTrace(...)`.
- Exposes `POST /api/chat`, `GET /health`, CORS `OPTIONS`.
- Returns `Object.assign(server, { traceStore })` for tests — **no HTTP read surface**.

Vite proxies only `/api/chat` ([`vite.config.ts`](../../vite.config.ts)). Browser UI calls Chat via [`createHttpChatProvider`](../../src/infrastructure/chat/http-chat-provider.ts); it never sees the server-side store.

### 3. Persistence layer (TASK-LLM-TRACE-001)

| Item | Value |
| --- | --- |
| Model | `LLMInteractionTrace` in `src/ai/trace/types.ts` |
| Registry | `{ version: 1, traces: LLMInteractionTrace[] }` |
| Storage key | `plt.llm_trace.v1` |
| Cap | `LLM_TRACE_MAX_ENTRIES = 200` (FIFO trim) |
| Store API | `load` / `append` / `clear` |
| Isolation | Forbidden keys prevent mixing with conversation/domain/layout |

Runtime on the Chat API process: in-memory `PreferenceStorage` map. Traces survive across chat requests **within one process** and are lost on API restart. That is acceptable for MVP inspectability; durable file/DB persistence is out of scope unless review expands it.

Browser `localStorage` is **not** where live Chat API traces land today. Wiring the viewer to browser preference storage would miss server-generated traces.

### 4. UI architecture

- Single-page React app; **no router**.
- Settings Menu (`App.tsx`) = locale / appearance / theme recipe only.
- Chat has `ContextInspector` (learning-context dump) — **not** LLM traces.
- No existing developer/debug panel, DevTools route, or observability UI.

### 5. Existing debug / developer tools

None productized. Closest analogs:

- Chat context overflow (`ContextInspector`) — learning context, not provider I/O.
- Playwright / Vitest harnesses — test tooling, not runtime inspection.
- Direct `traceStore` access in unit tests only.

## Architecture decisions

### AD-1 — Read path stays on the Chat API process (binding)

Traces are written server-side. The viewer must read the **same** `LlmTraceStore` instance that `withLlmTrace` appends to.

Rejected alternatives for MVP:

- Browser-only localStorage viewer (would not see live API traces).
- Dual-write to browser (unnecessary write-path change; couples UI to middleware).
- Domain/Workspace semantic persistence (violates store isolation and architecture rules).

### AD-2 — Keep process-local `plt.llm_trace.v1` as MVP persistence (binding)

Reuse existing store. Do **not** change schema version, field shapes, or append/trim semantics.

Optional additive store helpers only (non-breaking):

- `getById(id): Promise<LLMInteractionTrace | undefined>`
- `list(options?): Promise<LLMInteractionTrace[]>` — newest-first projection over `load()`

No file-backed store, IndexedDB, or remote analytics in this task.

### AD-3 — Minimal HTTP contracts on Chat API (binding)

Add read endpoints beside existing chat routes. Do not invent a second server.

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/api/llm-traces` | List traces (newest first) |
| `GET` | `/api/llm-traces/:id` | Full trace detail |
| `DELETE` | `/api/llm-traces` | Optional clear (developer hygiene; uses existing `clear`) |

List query params (MVP):

| Param | Type | Default | Behavior |
| --- | --- | --- | --- |
| `limit` | number | `50` (clamp 1–200) | Max items returned |
| `status` | `ok` \| `error` | omit | Optional filter |
| `projectId` | string | omit | Optional filter on `request.projectId` |

List payload uses a **summary DTO** so the list stays scannable; detail returns the full `LLMInteractionTrace`.

### AD-4 — Trace Viewer is a developer overlay, not product chrome (binding)

Entry: Settings Menu → “LLM Traces” (or equivalent i18n key). Opens a modal/panel overlay over the workspace.

Rejected for MVP:

- Primary nav / sidebar item
- Full client-side router / new SPA page
- Embedding inside Chat or Inspector product surfaces

### AD-5 — Do not change TASK-LLM-TRACE-001 write behavior (binding)

No changes to `buildTrace`, provider middleware success/error contract, DeepSeek/Mock internals, or Chat `POST /api/chat` response shape — except shared CORS/method headers if needed for new verbs.

### AD-6 — Out of scope (binding)

Memory · Learning Controller · Prompt Optimization · scoring/evaluation · prompt replay · A/B · cost dashboards · multi-user auth · exporting to third-party observability.

**Suggested route sketch:**

```text
GET /api/llm-traces?limit=50&status=error&projectId=p1
→ 200 {
  traces: LlmTraceListItem[],
  total: number          // total matching before limit
}

GET /api/llm-traces/:id
→ 200 LLMInteractionTrace
→ 404 { error: "Trace not found" }

DELETE /api/llm-traces
→ 204 {}
```

**`LlmTraceListItem` (proposed):**

```ts
{
  id: string;
  createdAt: string;
  durationMs: number;
  provider: string;
  model?: string;
  status: "ok" | "error";
  inputPreview: string;      // truncated input for list rows
  projectId?: string;
  nodeId?: string;
  suggestionCount?: number;  // from response when status=ok
  errorMessage?: string;     // from error when status=error
}
```

CORS: extend Allow-Methods to include `GET,DELETE` (already allows `GET,POST,OPTIONS`).

### Phase 3 — Client fetch module

**New:**

- `src/infrastructure/llm/trace-api.ts` (or `src/infrastructure/chat/http-trace-client.ts`)

  - `clearTraces(baseUrl)` optional

Base URL derivation: same origin convention as chat (`VITE_CHAT_API_URL` dirname or fixed `/api/llm-traces` when chat is `/api/chat`). Prefer explicit `VITE_CHAT_API_URL`-relative resolution documented in config guide — smallest option is hardcoding `/api/llm-traces` under the Vite proxy (mirrors chat).

Do **not** put HTTP client code in Domain or Application.

### Phase 4 — Trace Viewer UI

**New:**

- `src/ui/dev/LlmTraceViewer.tsx` — list + detail split

**UI behavior (MVP):**

1. Open from Settings.
2. Fetch list on open; show empty state when none.
3. Click row → fetch detail (or use list payload if already full — prefer detail GET for single source of truth).
4. Show status badge, provider/model, duration, project/node ids, full input, answer or error.
5. Optional “Clear traces” with confirm (reuse `ConfirmDialog` if present).
6. Refresh control.

Viewer must degrade when Chat API is down / unconfigured (clear error message; do not crash App). Stub-provider mode (no `VITE_CHAT_API_URL`) shows “Chat API not configured” rather than a fake local store.

## Data flow

```text
Developer opens Settings → LLM Traces
  → UI GET /api/llm-traces (via Vite proxy → Chat API)
  → Chat API: traceStore.load() → filter/sort/limit → LlmTraceListItem[]
  → UI renders list

Developer selects row
  → UI GET /api/llm-traces/:id
  → Chat API: getById / find in registry
  → UI renders LLMInteractionTrace detail

(unchanged write path)
Node Chat send
  → POST /api/chat
  → withLlmTrace(provider).complete(...)
  → store.append(LLMInteractionTrace)
```

Layering:

```text
UI (dev viewer)
  → Infrastructure HTTP client
  → Chat API (server)
  → ai/trace LlmTraceStore
```

Domain / Application / Conversation / Workspace semantic stores are not on this path.

## API contracts (normative for implementation)

### List

`GET /api/llm-traces`

Success `200`:

```json
{
  "traces": [
    {
      "id": "…",
      "createdAt": "2026-08-24T00:00:00.000Z",
      "durationMs": 120,
      "provider": "deepseek",
      "model": "deepseek-reasoner",
      "status": "ok",
      "inputPreview": "What should I focus on next?",
      "projectId": "p1",
      "nodeId": "n1",
      "suggestionCount": 2
    }
  ],
  "total": 1
}
```

Ordering: `createdAt` descending (newest first). `total` = match count before `limit`.

### Detail

`GET /api/llm-traces/:id`

Success `200`: body is a single `LLMInteractionTrace` (existing type; no schema bump).

Missing: `404 { "error": "Trace not found" }`.

### Clear (optional but recommended)

`DELETE /api/llm-traces` → `204` empty body after `traceStore.clear()`.

### Errors

Malformed query → `400`. Unexpected failure → `500`/`502` consistent with chat API style (`{ "error": string }`).

## Risk assessment

| Risk | Impact | Mitigation |
| --- | --- | --- |
| Process-local store lost on API restart | Developers may think viewer is broken | Document clearly; empty state copy explains process lifetime; do not pretend durability |
| Accidental write-path churn | Regresses TASK-LLM-TRACE-001 | Freeze middleware/schema; only additive store reads + HTTP |
| Proxy gap (`/api/chat` only) | Viewer 404 in Vite | Add `/api/llm-traces` proxy in same change set |
| Stub chat mode (no API URL) | Confusing empty/errors | Explicit “Chat API not configured” empty state |
| Large answers in list | Noisy UI / payload | Summary DTO + `inputPreview` truncation; full body only on detail |
| Treating viewer as product feature | Scope creep into eval/memory | Keep under Settings/dev; no Domain coupling |
| Unauthenticated local HTTP | Traces readable on localhost | Acceptable for local-first MVP; no auth in this task |
| CORS / method mismatch | Browser DELETE/GET blocked | Update Allow-Methods with routes |
| Filtering complexity | Schedule slip | Ship `limit` + optional `status`/`projectId` only |
